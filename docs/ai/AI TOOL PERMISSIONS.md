# AI Tool Permissions

## Purpose
This document defines which tools/functions an AI model is allowed to invoke for a given engine and task, and the permission-scoping rules that prevent a model from taking an action outside its intended boundary — reading data it should not see, writing data it should only draft, or invoking an external provider action beyond what the calling engine authorized. This is the access-control layer for AI tool-calling, distinct from the tool-calling execution mechanics themselves.

## Scope
Covers the permission model for tool/function definitions exposed to a model during a request: which tools exist, which engine/task pairs may use which tools, whether a tool is read-only or mutating, and whether a mutating tool requires human confirmation before executing. Does not cover the runtime mechanics of dispatching a tool call and returning its result to the model — see [architecture/06 AI TOOL CALLING ENGINE.md](../architecture/06%20AI%20TOOL%20CALLING%20ENGINE.md). Does not cover prompt content — see [AI PROMPT REGISTRY.md](AI%20PROMPT%20REGISTRY.md).

## Responsibilities
- Maintain a registry of tool definitions available anywhere on the platform, each tagged with what it can read, what it can write (if anything), and which external system (if any) it ultimately reaches through the Integration Gateway.
- Define, per engine/task, the explicit allow-list of tools that task's model call may be offered — a model is never offered a tool outside its task's allow-list, even if that tool exists in the registry.
- Classify every tool as **read-only** (safe to execute without confirmation), **mutating-project-data** (writes within the researcher's own `ResearchProject`, may auto-execute per engine policy), or **mutating-external** (would take an action on a real third-party system, e.g. submitting somewhere) — the last class must never be auto-executed without explicit human confirmation, since Core Contract #7 forbids any component from acting as a publisher itself.
- Enforce that no tool definition offered to a model grants direct provider access — every tool that reaches an external system does so only by calling the Integration Gateway or Multi-Model AI Gateway, never a direct SDK/API call embedded in the tool implementation, per Core Contracts #3 and #4.
- Record every tool invocation (tool name, engine, project, parameters, result, whether human-confirmed) for audit and for tracing an unexpected side effect back to its origin.

## Non-Responsibilities
- Does not implement the tool-calling loop (offering tools to the model, parsing the model's requested call, executing it, returning the result) — see [architecture/06 AI TOOL CALLING ENGINE.md](../architecture/06%20AI%20TOOL%20CALLING%20ENGINE.md).
- Does not implement the tools themselves (the actual read/write logic) — those live in the owning engine or in the Integration Gateway's adapters.
- Does not decide prompt wording that instructs a model on when to use a tool — see [AI PROMPT REGISTRY.md](AI%20PROMPT%20REGISTRY.md).
- Does not manage provider credentials used by a tool's downstream call — see [AI BYOK STRATEGY.md](AI%20BYOK%20STRATEGY.md) and the Integration Gateway's secrets handling.
- Does not decide whether a mutating-external action is appropriate for a given piece of research (an editorial/workflow judgment) — it only enforces that such an action cannot execute without human confirmation.

## Core Components
- **Tool Registry** — the catalog of all defined tools with their read/write classification and downstream system.
- **Engine Allow-List** — the per-engine/task mapping of which registry tools that task's model invocation may be offered at all.
- **Confirmation Gate** — the enforcement point that blocks any `mutating-external` tool call from executing until an explicit human confirmation action is recorded, regardless of how confidently the model requested it.
- **Invocation Log** — the audit trail of every tool call actually executed, successful or not.

## Owned Data
- `ToolDefinition` (name, description, parameter schema, classification: read-only / mutating-project-data / mutating-external, downstream system reference).
- `EngineToolAllowList` (engine/task id → list of permitted `ToolDefinition` ids).
- `ToolInvocationRecord` (tool id, engine, project id, request id, parameters, result summary, confirmation status, timestamp).

## Inputs
- Tool-call requests generated by a model mid-conversation, arriving through the tool-calling execution layer.
- Engine-declared allow-lists, set by whoever owns each engine's task definition.
- Human confirmation actions for gated `mutating-external` calls.

## Outputs
- The permitted-tool subset offered to the model for a given request, filtered through the Engine Allow-List before the request ever reaches the Multi-Model AI Gateway.
- Execution results returned to the model (for read-only and confirmed mutating calls) or a blocked/pending status (for unconfirmed `mutating-external` calls).
- The Invocation Log, consumed for audit and incident investigation.

## Extension Points
- A new tool is added to the Tool Registry with a classification and downstream reference; it grants no engine access until explicitly added to that engine's Allow-List.
- A new engine defines its own Allow-List by selecting from existing registry tools, requesting a new tool only when no existing one fits, keeping tool proliferation centrally visible.
- Confirmation UX for `mutating-external` calls can evolve (single confirm, itemized multi-step confirm for batch actions) without changing the underlying classification contract.

## Security & Privacy
- The Confirmation Gate is a hard boundary, not a UI suggestion: a `mutating-external` tool call must be unexecutable at the code level without a recorded confirmation, not merely discouraged by prompt wording — prompt instructions alone are not a security control.
- Tool parameter values may contain private project content; the Invocation Log stores them under the same access rules as the source `ResearchProject`, consistent with Core Contract #9.
- No tool definition may embed a provider credential directly — credentials are resolved at execution time by the Integration Gateway, never passed to or through the model, consistent with [AI BYOK STRATEGY.md](AI%20BYOK%20STRATEGY.md).

## Failure Modes
- **Over-broad allow-list** — an engine is granted a tool it does not actually need for its task, widening the model's effective capability beyond intent; mitigated by treating allow-list grants as least-privilege by default, reviewed when an engine's task scope changes.
- **Misclassified tool** — a tool that reaches an external system is mistakenly registered as `mutating-project-data`, bypassing the Confirmation Gate; mitigated by requiring any tool whose downstream reference is outside the platform's own database to default to `mutating-external` unless explicitly reviewed otherwise.
- **Confirmation bypass under retry/fallback** — a fallback model path (Core Contract #11) re-requests a gated action without re-triggering confirmation; mitigated by keying the Confirmation Gate to the request/action, not to the model that requested it.

## Observability
- Tool invocation volume per tool, per engine, to catch unexpected usage patterns.
- Rate of `mutating-external` calls blocked pending confirmation versus actually confirmed, and time-to-confirmation.
- Count of tool-call attempts rejected for being outside an engine's allow-list — a nonzero rate here signals either a prompt-engineering issue or a misconfigured allow-list.

## P0/P1/P2/P3
**P0.** Any tool-calling capability offered to a model without an enforced permission boundary risks an unauthorized read, write, or external action; the allow-list and Confirmation Gate must exist before tool-calling is enabled for any engine.

## Current Status
Documented, not implemented. No Tool Registry, allow-list enforcement, or Confirmation Gate exists yet. [architecture/06 AI TOOL CALLING ENGINE.md](../architecture/06%20AI%20TOOL%20CALLING%20ENGINE.md) is referenced here as the planned execution-layer counterpart.

## Open Questions
- Whether `mutating-project-data` tools should ever require confirmation for high-impact operations (e.g. deleting a large evidence set) or remain auto-executing by definition.
- Who reviews and approves a new tool's classification before it enters the registry — not yet assigned.
- Whether the Confirmation Gate UX differs between synchronous chat interactions and async background-job-initiated tool calls.
- How tool allow-lists interact with AI Compare Mode, where multiple models may propose different tool calls for the same task — see [AI COMPARE MODE.md](AI%20COMPARE%20MODE.md).
